# 写作技巧库

从优质公众号文章中提取的可复用写作手法。持续积累。

---

## 技巧 1：图文配合的"三段式"注解法

**描述**：展示图片时，避免"看图说话"的啰嗦，又保证信息量。

**原文示例**：
- 图片上方：简要引言（"先看效果"）
- 图片本身：核心视觉信息
- 图片下方：【该图片的描述】标签 + 结构化数据（表格、列表）

👉 **应用建议**：写 AI 生成图片/图表的文章时，务必在图片下方用 Markdown 表格或列表解释图中关键元素。

---

## 技巧 2：技术细节的"颗粒度控制"

**描述**：不停留在"好用"的表面，深入到工程审美层面，拉开与普通测评文的差距。

**原文示例**：
- 提到具体字体（JetBrains Mono）
- 对比"糖果色 UI"和"深色工程风"
- 解释 SVG 的图层绘制顺序（Arrow behind components）

👉 **应用建议**：写 AI 工具时，多提一句"审美偏好"或"底层实现逻辑"，能瞬间拉开与普通测评文的差距。

---

## 技巧 3：Prompt/代码的"透明化"展示

**描述**：不仅给结果，还把中间的"原材料"给出来。

**原文示例**：
- 展示生成的 HTML 代码前几行
- 给出可直接复制的 Prompt 模板（如 `Analyze this codebase...`）

👉 **应用建议**：凡是教人用 AI 的文章，一定要把成功的 Prompt 原文贴出来，这是读者最关心的干货。

---

## 技巧 4：真诚 + 略带调侃的语言风格

**描述**：技术文不枯燥，用第一人称感受增加真实感。

**原文示例**：
- "真心懒得做的"、"就这？"等口语化表达
- "顺手写篇文章"、"个人比较喜欢"等主观视角

👉 **应用建议**：适当加入第一人称感受（如"我更喜欢这种方式，因为……"），阅读体验更好。但不要刻意卖萌或过度吐槽。

---

## 技巧 5：表格密集对比法

**描述**：凡是并列选项、功能对比、配置项，一律用表格而非段落罗列。表格是技术文章中信息密度最高的呈现方式。

**原文示例**：
- 内置 Agent 对比表（Agent | 特点）
- 快捷键速查表（快捷键 | 功能）
- 关键词触发模式表（关键词 | 触发模式）
- 决策引导表（场景 | 推荐方式）

👉 **应用建议**：写技术教程时，只要有 2 个以上的并列项，优先考虑用表格。表格列数控制在 2-3 列，每列保持简短。

---

## 技巧 6：概念先行原则

**描述**：先花篇幅把核心概念讲透，再讲操作。读者理解了"为什么"之后，操作章节可以写得很简短。

**原文示例**：
- 在"核心概念"章节开头声明："这是理解 OpenCode 的关键"
- 用独立小节（3.1-3.4）分别讲解 Agent 类型、@用法、Tab切换、快捷键
- 每个概念配表格和代码示例

👉 **应用建议**：写工具教程时，不要急于上操作步骤。先问"读者需要先理解什么才能看懂后面的操作？"把这部分放在最前面。

---

## 技巧 7：复杂度分级场景法

**描述**：同一类任务按小/中/大三个复杂度展示不同用法，覆盖不同水平的读者需求。

**原文示例**：
```
小功能（1-2 个文件）：直接 Build Agent
中等功能（多文件联动）：Plan → Build
大型功能（跨模块）：ulw 或 /start-work
```

👉 **应用建议**：教人用工具时，不要只写一种场景。按复杂度分级，让新手和进阶读者都能找到适合自己的用法。

---

## 技巧 8：决策引导表

**描述**：当工具提供多种方式完成类似任务时，用对比表格帮读者做选择。

**原文示例**：
| 场景 | 推荐方式 |
| 思路清晰的单一功能 | `ulw` |
| 需求有模糊点，想先确认方案再动手 | `Tab → Prometheus → /start-work` |
| 复杂架构任务，需要深度独立执行 | `Tab → Hephaestus` |

👉 **应用建议**：只要工具/方法有"选择困难"的可能，就加一张决策引导表。格式固定：场景列 + 推荐方式列。

---

## 技巧 9：⚠️ 警告/提示 blockquote

**描述**：关键的易错点、常见误解、重要注意事项用 ⚠️ 开头的 blockquote 突出显示。

**原文示例**：
> ⚠️ 常见误解：Tab 不是"切换 Plan/Build 模式"，而是切换两个独立的主 Agent。

👉 **应用建议**：每个关键概念后面检查一下"读者可能会怎么误解？"，把最常见的误解用这种格式提前澄清。

---

## 技巧 10："最重要的一个词"提炼法

**描述**：从工具的众多功能中提炼一个核心关键词，在文章中反复强调，让读者记住一个抓手。

**原文示例**：
- "ulw（ultrawork 的缩写）是 oh-my-opencode 的核心关键词。"
- 后续场景中反复使用 ulw 作为解决方案
- 单独小节详细解释 ulw 的含义和用法

👉 **应用建议**：每篇工具教程找一个"抓手词"。在引言中首次引出，中间重点讲解，场景中反复使用。让读者即使忘了所有细节，也能记住这一个关键词。

---

## 技巧 11：FAQ 兜底法

**描述**：文末用 Q&A 格式解答读者看完前面章节可能还困惑的问题，降低留言咨询的门槛。

**原文示例**：
- Q：@ 引用文件和 @mention Agent 如何区分？
- Q：Tab 切换 Agent 和 Ctrl+T 切换模型变体有什么区别？
- Q：/start-work 中断了怎么办？

👉 **应用建议**：写完文章后自问"读者看完最可能还困惑什么？"选 5-8 个问题简洁回答。特别适合容易混淆的概念对比、异常场景处理。
